# 변경 검증

## 검증 경계

- 검증 단계에서 제품 코드·설정·문서를 수정하지 않는다. 테스트 작성이 배정된 test/main/구현자는 소유한 테스트만 작성·수정할 수 있다. 검증 전용 배정은 모든 소스 편집을 금지한다.
- 테스트 실행 산출물은 필요 근거만 별도 경로로 보고하고 소스 diff/커밋에 무조건 포함하지 않는다.
- 완료 조건과 관찰 가능한 기대 결과가 없는 경우, 추정으로 통과를 선언하지 않고 누락된 기준을 보고한다.

## 검증 절차

1. 대상 변경, 환경, 입력, 기대 결과를 명시해 재현 절차를 고정한다.
2. 가장 직접적인 테스트부터 실행하고, 필요할 때만 통합·회귀 범위로 넓힌다.
3. 명령, 핵심 출력, 종료 상태, 환경 차이를 기록한다.
4. 결과를 완료 조건별로 대조하고, 통과·실패·판단 불가를 분리한다.

## 실패 분류

- `구현 결함`: 기대 동작과 실제 동작이 다르며 재현 가능하다.
- `테스트 결함`: 테스트의 기대값·격리·준비가 잘못되었다.
- `환경·도구 문제`: 의존성, 권한, 네트워크, 플랫폼 등 코드 밖의 문제가 원인이다.
- `검증 부족`: 필요한 입력, 관찰 신호, 접근 권한 또는 완료 기준이 없다.

## 보고 형식

- 재현 절차와 실행한 명령
- 완료 조건별 결과와 근거
- 실패 분류, 최소 재현, 관련 로그 또는 경로
- 제품 수정이 필요하면 실패 원인과 필요한 좁은 범위를 반환한다. 구현 담당자는 자신의 구현 단계로 돌아가 수정하고 검증을 다시 수행한다; test는 제품 코드를 수정하지 않는다.

## 역할별 선택
사용자 명시 호출 또는 설치된 역할별 사용 조건이 맞을 때만 필요한 절차를 읽는다. 전 단계를 모든 작업에 반복하지 않는다. 역할·파일 소유권과 read-only 제한은 항상 유지한다.

## 완료 근거
완료 주장은 현재 변경본에 대한 검증으로 뒷받침한다. 명령·종료 코드·대상·통과/실패/미실행을 구분한다. lint 통과를 build 통과로, 일부 테스트 통과를 전체 통과로, 하위의 자기 보고를 독립 확인으로 바꾸지 않는다. 이미 검증한 동일 diff/환경에 변경이나 새 실패 근거가 없다면 의식적으로 같은 테스트를 반복하지 않는다.
