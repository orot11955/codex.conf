# 측정과 재검증

## 기준 기록
대상 URL(비밀 query는 제거), 작업 단계, 커밋/빌드, 개발/프로덕션 모드, 브라우저, 뷰포트, CPU/네트워크 제한, 로그인/tenant, 데이터 행 수, cold/warm cache를 기록한다. 개발모드 수치와 프로덕션 수치를 비교하지 않는다.
이미 있는 RUM/현장 지표가 제공되면 우선순위 판단에 쓰되 개인정보·외부 데이터 업로드 범위를 지킨다. 브라우저 trace는 원인 진단을 보완한다. 현장과 실험실 측정은 서로 대체하지 않는다.

## 진단 순서
요청 waterfall/TTFB → 전송 리소스와 주요 이미지 발견 시점 → JS parse/long task → 렌더·layout·입력 지연 → 불필요한 요청/재렌더를 실제 근거로 좁힌다.
API/DB가 원인이면 frontend에서 무작정 debounce·skeleton을 늘리지 말고 main에 담당 경로를 전달한다. 개선안이 캐시라면 키의 사용자/권한/tenant와 무효화 조건부터 확인한다.
긴 목록은 실제 입력·스크롤 지연과 행 수, 접근성·인쇄·검색 요구를 본 뒤 pagination/content visibility/virtualization의 비용을 비교한다. 특정 라이브러리를 자동 추가하지 않는다.

## 결과
before/after, 단위, 동일 조건 여부, 시행 횟수와 편차를 남긴다. 단일 측정이면 그 한계를 표시한다. 실측하지 않은 절감률을 계산하지 않는다. 현장 개선은 배포 후 새 데이터가 모이기 전까지 미검증이다.
기존 프로젝트 test/build 명령을 사용하며 도구가 없으면 실행하지 않은 이유와 재현 가능한 다음 명령을 남긴다. 도구 설치를 했다고 성능 검증 완료로 간주하지 않는다.
