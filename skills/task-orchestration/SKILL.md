# 작업 오케스트레이션

## 적용 판단

이 전체 절차는 사용자 명시 요청 시에만 읽는다. 먼저 메인 세션이 직접 완료할 수 있는지 판단한다. 위치와 방법이 명확하거나 한 역할의 단일 작업이면 직접 수행한다. 다음 중 하나가 있을 때만 하위 에이전트를 추가한다.

- 구현 전 실행 경로나 영향 범위를 별도로 조사해야 함
- 공개 계약, DB, 인증·권한 또는 큰 구조 결정을 먼저 확정해야 함
- 독립된 파일 소유권으로 병렬 처리할 두 작업이 있음
- 구현자와 분리한 검증 또는 고위험 검토가 완료 조건에 필요함

## 최소 역할 선택

- `scout`: 경로·흐름·영향 범위가 불명확할 때만 읽기 전용 조사
- `architect`: 새 계약·DB·보안·대규모 구조 결정이 있을 때만 읽기 전용 설계
- `frontend`, `backend`, `executor`: 실제 변경 영역에 가장 가까운 구현 역할 1개가 기본
- `test`: 별도 검증의 실익이 있을 때 실행한다. 테스트 파일 소유권을 받은 경우에만 테스트를 작성하고, 검증 전용 배정에서는 어떤 소스도 수정하지 않는다.
- `critic`: 자동 검증 뒤에도 고위험 논리·회귀 판단이 남을 때 최대 1회
- `security`: 인증·권한, 비밀정보, 외부 입력, 파일·URL·명령, 외부 통신 또는 공급망 경계가 바뀔 때만 사용

필요한 품질을 만족하는 최소 집합으로 시작하고, 확인된 부족 때문에만 다음 역할을 추가한다. 같은 조사·구현·검증을 반복 배정하지 않는다.

## 분해와 소유권

1. 목표, 완료 조건, 알려진 사실과 미확인 사항을 구분한다.
2. 선행 조사·설계를 먼저 끝내고 결과에 의존하는 구현을 나중에 배정한다.
3. 한 파일에는 한 명의 현재 소유자만 둔다. 공유 계약, Migration, 환경 설정과 lockfile은 병렬 수정하지 않는다.
4. 기본 1~2개, 독립된 작업만 최대 3개 병렬화한다. 하위 에이전트의 재위임은 금지한다.
5. 파일 경계나 성공 기준을 정할 수 없으면 구현을 배정하지 말고 필요한 조사 또는 사용자 결정을 보고한다.

## 배정 형식

런타임이 지원할 때 `fork_turns="none"`과 아래 `목표`, `근거`, `소유권`, `제약`, `완료 조건`, `검증 방법`, `선택 스킬` 일곱 필드의 짧은 컨텍스트만 사용한다.

- `목표`: 완료된 상태를 한 문장으로 작성
- `근거`: 관련 경로·심볼, 확인된 선행 결과와 필요한 계약
- `소유권`: 역할, 읽기 범위, 수정 대상과 금지 경로
- `제약`: 금지사항과 보존할 동작
- `완료 조건`: 산출물과 `변경`, `검증`, `위험` 인계
- `검증 방법`: 절차와 성공 기준
- `선택 스킬`: 역할별 조건에 맞는 이름·사용 이유만 전달; 본문 전체 전달 금지

전체 대화, 긴 로그, 전체 파일과 관련 없는 후보를 전달하지 않는다. 모델·추론 설정은 역할 파일의 기본값을 사용하고 사용자 요구나 명확한 품질 근거가 있을 때만 덮어쓴다.

## 통합과 실패 처리

1. 결과를 배정 범위와 완료 조건에 직접 대조한다.
2. 하위 결과에서는 `변경`, `검증`, `위험`만 추려 중복 없이 통합한다.
3. 실패를 구현 결함, 요구사항 누락, 환경 문제, 검증 부족 또는 소유권 충돌로 분류한다.
4. 원인에 맞는 하나의 좁은 작업으로만 재지시한다. 같은 실패가 반복되면 재시도를 멈추고 조사·설계 또는 사용자 결정으로 전환한다.
5. 필수 검증과 남은 위험을 확인한 뒤 메인 세션이 최종 완료를 판정한다.
