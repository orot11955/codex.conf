# 변경 설계

## 설계 입력

- 탐색으로 확인된 현재 동작, 요구사항, 제약, 영향 범위를 사용한다.
- 핵심 사실이 부족하면 가정을 사실처럼 채우지 말고 추가 탐색 항목으로 돌려보낸다.

## 설계 산출물

다음 내용을 짧고 결정 가능하게 작성한다.

1. 목표와 비목표: 바꾸는 사용자·시스템 동작과 의도적으로 바꾸지 않는 범위를 정한다.
2. 변경 경계: 소유 파일·모듈, 외부 의존성, 호출 경계를 정한다.
3. 계약: 입력·출력, 오류, 권한, 호환성, 관찰 가능한 동작을 정의한다.
4. 데이터: 스키마·상태 변경, 마이그레이션 순서, 이전 버전과의 공존 여부를 정한다.
5. 배포 안전성: 기능 플래그, 순차 배포, 롤백 조건과 관찰 신호를 적는다.
6. 검증: 단위·통합·수동 확인 중 필요한 방법과 각 성공 기준을 적는다.

## 구현 가능성 점검

- 한 구현 에이전트가 소유할 수 있는 파일 경계로 계획을 나눈다.
- 공유 파일 수정이 필요하면 순서와 최종 통합 소유자를 명시한다.
- 계약 변경에는 호출자·피호출자·테스트의 동시성 및 호환성 위험을 적는다.
- 되돌릴 수 없는 변경에는 백업 또는 복구 경로를 포함한다.

## 인계 형식

구현 작업마다 목표, 수정 가능 경로, 비수정 경로, 완료 조건, 검증 명령 또는 절차를 제공한다. 설계는 구현을 대신하지 않으며, 코드나 파일을 직접 수정하지 않는다.

## 역할별 선택
사용자 명시 호출 또는 설치된 역할별 사용 조건이 맞을 때만 필요한 절차를 읽는다. 전 단계를 모든 작업에 반복하지 않는다. 역할·파일 소유권과 read-only 제한은 항상 유지한다.
